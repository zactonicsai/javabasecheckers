Build Guide · v1.0

Building secure Java 25 applications with quality and security checkers.

A practical, defense-in-depth setup for Spring Boot 4 projects. Six tools, one Maven build, every commit verified against the same bar that catches CVEs, weak crypto, injection flaws, and style drift before they reach production.

01 · Get going

Quick start

Three commands. The first run of the full verify will be slow because OWASP Dependency-Check downloads the NVD database — set NVD_API_KEY first to avoid rate limiting.

1. Run the app

mvn spring-boot:run

2. Run all quality + security gates

export NVD_API_KEY="your-key-here"   # get one from nvd.nist.gov
mvn clean verify

3. Fast inner loop (skip CVE scan)

mvn verify -Ddependency-check.skip=true

Reports land in target/ after verify: jacoco/index.html, spotbugs.html, checkstyle-result.xml, pmd.xml, dependency-check-report.html.

02 · The stack

What's underneath

Java 25 is an LTS release with virtual threads, pattern matching, records, sealed classes, and stricter defaults around security primitives. Spring Boot 4 modularized its starters — spring-boot-starter-web became spring-boot-starter-webmvc, and many auto-configuration packages moved to web-stack-specific namespaces.

Framework

Build

Verify phase wired to JaCoCo, Checkstyle, PMD, SpotBugs+FindSecBugs, OWASP DC.

03 · Rationale

Why catch this at build time

The cost of fixing a vulnerability multiplies the further it travels. A weak hash in a developer's branch is a one-line change. The same code, deployed and breached, is a regulator notification, a press cycle, and months of forensic work.

Build-time gates compress that loop. Every mvn verify is a chance to catch the issue before it leaves the developer's machine — and a chance to catch it consistently across every developer, every branch, every CI run.

Static checkers won't find every bug. They will find a large class of common, mechanical mistakes — the ones humans miss in review because they're tedious to look for. SQL string concatenation. MessageDigest.getInstance("MD5"). A Jackson library four CVEs out of date.

This setup composes six checkers that overlap intentionally. Defense in depth at the build layer, the same way you'd apply it at the network or runtime layers.

04 · The toolchain

The six checkers

Each tool covers a different layer. Together they form the build-time security and quality gate. Click What & why on any card for deeper detail.

Style Source

Checkstyle

Enforces a coding style — formatting, naming, javadoc, structural rules.

What it catches: inconsistent indentation, line length, missing javadoc on public APIs, illegal imports, magic numbers, badly-named classes/methods/constants, switch statements without default, empty blocks.

Config: config/checkstyle.xml. The project ships a sensible default; you can also start from Google Java Style or Sun Java Style.

Phase: verify. Fails the build on any violation by default.

Static analysis Source

PMD

Source-level static analysis. Design smells, error-prone patterns, dead code, copy-paste.

Rulesets enabled: bestpractices, errorprone, security, multithreading, performance. Plus cpd-check for copy-pasted code blocks.

What it catches: empty catch blocks, unused private fields, suspicious string-to-BigDecimal, modifying a collection while iterating, returning null from a Collection method, missing break in switches.

Complements SpotBugs: PMD reads source (sees comments, formatting, design intent). SpotBugs reads bytecode (sees what actually executes). Running both is the standard pairing.

Static analysis Bytecode

SpotBugs

Bytecode-level bug pattern detection — the successor to FindBugs.

What it catches: null-pointer dereferences, infinite recursion, comparing String with ==, ignored return values, mutable static fields, resource leaks, broken equals/hashCode.

Configured at: effort=Max, threshold=Low — most thorough, lowest bar to report. Pairs with FindSecBugs (next).

Bytecode-level advantage: sees what the compiler actually produced, including issues that only appear after lambda desugaring, autoboxing, or generic erasure.

Security Bytecode

Find Security Bugs

SpotBugs plugin focused on OWASP Top 10 security defects in Java code.

128+ vulnerability types across 826+ API signatures. Covers Spring MVC, Servlets, Hibernate, JAX-RS, and more.

Categories: SQL/HQL injection, XSS, command injection, path traversal, XXE, SSRF, insecure deserialization, weak cryptography (MD5, DES, ECB), weak random for security tokens, hard-coded credentials, predictable HTTP cookies, weak TLS.

Taint analysis: follows untrusted input from request entry points through method calls to dangerous sinks — catches injection paths that aren't visible from a single method.

Security Dependencies

OWASP Dependency-Check

Software Composition Analysis (SCA). Scans every JAR for known CVEs.

How it works: identifies each dependency's CPE (Common Platform Enumeration), then cross-references against the NIST National Vulnerability Database to find associated CVEs.

Threshold: build fails on CVSS >= 7 (High/Critical). Adjust via dependency-check.failBuildOnCVSS property.

Outputs: HTML for humans, JSON for tooling, SARIF for GitHub Code Scanning upload.

False positives: manage via config/owasp-suppressions.xml. Justify each suppression and set an expiry.

Coverage Runtime

JaCoCo

Test coverage measurement and threshold enforcement.

What it measures: instruction, branch, line, complexity, method, and class coverage. We enforce 70% instruction coverage at the bundle level.

Why it matters for security: uncovered code paths often hide poor input validation. Coverage isn't a security tool, but low coverage on critical paths is a smell — the SAST tools above only flag what they can prove; tests exercise what's left.

Report: target/site/jacoco/index.html.

05 · Practice

Secure development workflow

Tools find what tools can find. The rest is process. Each phase below has a small number of disciplined practices — pick the ones that fit your team and apply them consistently.

01 Before you write code — design & threat model

Sketch the data flow. Where does untrusted input enter? Where does it cross a trust boundary? Where does sensitive data leave the system?

Apply STRIDE at the feature level: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege. Two of the six usually apply — write down which.

Choose the safe default before you start typing — parameterized queries, allowlists for path inputs, SecureRandom over Random for anything security-adjacent.

02 In the IDE — fast feedback while typing

Install the matching IDE plugins so issues show up as you write, not at mvn verify:

  • IntelliJ: SpotBugs, CheckStyle-IDEA, PMDPlugin, SonarLint
  • VS Code: SonarLint, Checkstyle for Java, SpotBugs
  • Eclipse: SpotBugs Eclipse Plugin, eclipse-cs

Point each plugin at the same config files the Maven build uses (config/checkstyle.xml, the PMD ruleset). One source of truth, no surprises in CI.

03 Before commit — pre-commit hooks & local verify

Run mvn verify -Ddependency-check.skip=true before pushing. Fast (~30 sec on this project), catches everything except the CVE scan.

Adopt a pre-commit hook (e.g. pre-commit framework) that runs Checkstyle and SpotBugs on staged Java files only.

Run gitleaks or trufflehog as a pre-commit step. Static analyzers find hardcoded credentials in code; secret scanners find them in everything else.

04 In code review — what humans should check

Reviewers focus on what tools can't see: business logic, trust assumptions, authorization checks at the right layer, error handling that doesn't leak information.

Specific things to ask in every Java PR: Is every external input validated at the boundary? Are exceptions logged without leaking secrets or stack traces to clients? Is every new dependency necessary? Is every new @Suppress* annotation justified in a comment?

If the PR adds an OWASP suppression, the reviewer reads the justification and checks the expiry date.

05 In CI — the same gate, for everyone

CI runs mvn clean verify with no skips. The OWASP NVD cache lives in CI cache storage between runs (~600MB).

Upload the SARIF report from Dependency-Check to GitHub Code Scanning so findings appear on the Security tab and can be tracked over time.

Run Dependabot or Renovate in parallel — they keep dependencies fresh; OWASP DC catches the ones that slipped through.

06 After deploy — runtime monitoring & DAST

SAST (the tools on this page) is half the picture. The other half is DAST — exercise the running app: OWASP ZAP or Burp Suite against the deployed staging build.

Wire runtime CVE alerts: Trivy on the deployed container image catches what slipped past the JAR-level scan.

Have an SBOM. CycloneDX Maven plugin emits one each build. If a future CVE drops on something you ship, you can answer "are we affected?" in seconds.

06 · Patterns

Good vs bad code

The same six issues show up in nearly every Java codebase. For each: what the checker reports, the bad version, the good version, the CWE.

SQL injection

CWE-89 Critical Caught by FindSecBugs (SQL_INJECTION_JDBC) 
// Concatenating user input into SQL = injection.
public List<User> findByName(String name) {
    String sql = "SELECT * FROM users WHERE name = '" + name + "'";
    return jdbc.query(sql, USER_ROW_MAPPER);
}
// name = "x' OR '1'='1" returns the whole table.
// Parameterized query. The driver escapes input correctly.
public List<User> findByName(String name) {
    String sql = "SELECT * FROM users WHERE name = ?";
    return jdbc.query(sql, USER_ROW_MAPPER, name);
}

Weak cryptography

CWE-327 High FindSecBugs (WEAK_MESSAGE_DIGEST_MD5, CIPHER_INTEGRITY) 
// MD5 has been broken for password hashing for decades.
// DES is 56-bit. ECB mode reveals patterns in plaintext.
MessageDigest md = MessageDigest.getInstance("MD5");
Cipher c = Cipher.getInstance("DES/ECB/PKCS5Padding");
// SHA-256+ for hashing. Argon2/BCrypt for passwords.
// AES-256-GCM for authenticated encryption.
MessageDigest md = MessageDigest.getInstance("SHA-256");
Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
// Use a per-message random 12-byte IV with GCM.

Path traversal

CWE-22 High FindSecBugs (PATH_TRAVERSAL_IN) 
// User-controlled filename, no validation.
// filename = "../../etc/passwd" reads outside the upload dir.
Path file = Paths.get("/var/uploads", filename);
return Files.readAllBytes(file);
// Resolve, normalize, then verify the result is inside the root.
Path root = Paths.get("/var/uploads").toAbsolutePath().normalize();
Path file = root.resolve(filename).normalize();
if (!file.startsWith(root)) {
    throw new SecurityException("Path traversal attempt");
}
return Files.readAllBytes(file);

Hardcoded credentials

CWE-798 Critical FindSecBugs (HARD_CODE_PASSWORD, HARD_CODE_KEY) 
// In source. In git history. In every backup forever.
private static final String DB_PASSWORD = "Pa55word!";
private static final String API_KEY = "sk_live_a1b2c3d4...";
// Inject from environment / secret manager / Spring config.
@Value("${db.password}")     // Spring resolves from env/vault
private String dbPassword;

// Or via Spring Cloud Vault, AWS Secrets Manager, etc.

Swallowed exceptions

CWE-390 Medium PMD (EmptyCatchBlock), SpotBugs (DE_MIGHT_IGNORE) 
try {
    riskyOperation();
} catch (IOException e) {
    // ignore - we'll just continue
}
// Now the failure mode is silent. Good luck debugging.
try {
    riskyOperation();
} catch (IOException e) {
    log.warn("Operation failed, continuing with default", e);
    // OR: throw new ServiceException("operation failed", e);
}

Insecure randomness for security tokens

CWE-338 High FindSecBugs (PREDICTABLE_RANDOM) 
// java.util.Random is predictable from a few samples.
Random r = new Random();
String token = Long.toHexString(r.nextLong());  // session token
// SecureRandom is the only choice for tokens, salts, IVs, nonces.
SecureRandom r = new SecureRandom();
byte[] bytes = new byte[32];
r.nextBytes(bytes);
String token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);

XML External Entity (XXE)

CWE-611 High FindSecBugs (XXE_DOCUMENT, XXE_SAXPARSER) 
// Default parser resolves external entities — file read / SSRF.
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
DocumentBuilder db = dbf.newDocumentBuilder();
Document doc = db.parse(input);
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
dbf.setXIncludeAware(false);
dbf.setExpandEntityReferences(false);
DocumentBuilder db = dbf.newDocumentBuilder();
Document doc = db.parse(input);
